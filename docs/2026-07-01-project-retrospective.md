# 项目回顾 — 韩语 YouTube 中文字幕插件

最后更新：2026-07-01

---

## 一、项目背景与定位

**解决的问题**：韩语游戏主播在中文圈有大量死忠粉，但 YouTube 没有实时中文翻译。现有替代方案是等别人人工搬运熟肉，时效慢（几天到几周）、覆盖差（只搬热门高光，长直播/冷门主播几乎没有）。

**价值主张**：不是"比搬运翻得更好"，而是"搬运没覆盖到的内容 / 你现在就想看的内容，立刻能大致看懂"。对照组是"根本没熟肉、完全看不懂"，所以大致看懂就是从 0 到 1 的胜利。

**冷启动策略**：挑 1–2 个中文圈有死忠、但搬运覆盖差的韩语主播，去其粉丝聚集地（超话/QQ 群/贴吧/Discord）精准投放。死忠粉痛点最尖锐、最愿装插件、最能自发安利，且能容忍 v1 的粗糙。

---

## 二、整体架构

```
Chrome 插件（核心，v1 已上线）
├── content.js        监听字幕 DOM → 发消息给 background
├── background.js     接收消息 → 调 Google 翻译 → 返回中文 + 缓存
├── popup.html/js     开关 UI + 状态指示
├── src/translate.js  翻译引擎封装（可替换层）
└── styles.css        字幕叠加层样式

后端（后续阶段，feature 已完成待部署）
├── FastAPI           REST API + WebSocket
├── PostgreSQL        users / history_records / vocabulary_notebook
└── 部署目标：Render 或 Railway

Web 控制台（后续阶段，基础脚手架已建）
└── React + Vite      用户注册、生词本、历史记录
```

## 三、已完成功能

### 阶段 1：v1 Chrome 插件（2026-06-24 完成）

**核心流程**：
```
用户打开韩语 CC → content.js MutationObserver 监听字幕容器
→ 抓到新韩语文字 → 发消息给 background.js
→ background 调 Google 翻译接口（ko→zh-CN）+ 翻译缓存
→ content.js 把中文叠加在字幕下方
```

**关键设计决策**：
- **纯前端，零后端**：v1 用免费 Google 翻译非官方接口，无需 API key、装上即用
- **翻译引擎封装为可替换层**（`src/translate.js`）：接口挂了或要换引擎（Claude/DeepL），只动这一层
- **背景页发起翻译请求**：绕开 content script 的跨域（CORS）限制
- **接受接口风险**：非官方接口可能限流，v1 接受此风险换零成本快速验证

**实现细节**：
- 防抖 + 缓存：相同字幕不重复请求，高频变化合并
- 失败回退：接口失败时显示原韩语，不崩溃不空白
- 开关持久化：状态存 `chrome.storage.local`，重开浏览器后保留

### 阶段 2：后端 history_records 存储（2026-06-25 完成，待部署）

**背景**：支撑后续阶段的「用户看过哪些视频」功能（账号体系），不属于 v1。

**关键设计决策 — 只存视频级元数据，不存字幕正文**：
- 逐句存储每条字幕：一场 2 小时直播 ≈ 2000–3000 条 ≈ 0.7MB，约 800 场就撑满 Supabase 免费额度（500MB）
- 用户实际需求只是"有一个看过的视频列表"——只需存 `video_id`、`title`、`channel`、`watched_at`、`last_position`
- 缩略图不入库，前端用 `video_id` 拼 YouTube 缩略图 URL

**存储控制策略（三重保险）**：
1. 只存视频元数据 → 省掉 ~99% 数据量
2. upsert：重看同一视频只更新时间，不增行数
3. 每用户硬上限 200 条：超出时删除最旧一条

**估算**：200 条 × 250 字节 ≈ 50KB/人，1 万用户全满 ≈ 500MB，存储永不随观看次数无限增长。

**完成状态**：全部 5 个任务通过，14 个单元测试全绿，最终 Opus 代码审查通过（无 Critical 问题）。

---

### 阶段 3：Popup 状态指示器（2026-07-01 完成）

在 popup 开关下方加一行状态文字 + 彩色圆点：
- 启用：绿点 + "已启用，监听字幕中…"
- 关闭：灰点 + "翻译已关闭"
- 切换即时生效，纯 CSS `::before` 实现圆点，无图片依赖

---

### 阶段 4：体验打磨（2026-07-01 完成）

实测过程中发现并修复的问题：

| 问题 | 原因 | 修复 |
|------|------|------|
| 中文译文出现 `>>` | 多人视频的 CC 文件用 `>>` 标注换人，原文就有 | `currentCaptionText()` 拼接后全局 replace，翻译前去掉 |
| 翻译延迟偏高，快速说话时跟不上 | 防抖 250ms + 每次翻译都读一次 storage | 防抖降至 100ms；`enabled` 状态内存缓存，`onChanged` 同步 |
| 字幕消失后中文一直残留 | 无清除逻辑，旧译文挂到下一条字幕才替换 | 字幕消失 1 秒无新输入则隐藏；1 秒内有新字幕取消计时器立即翻译 |

## 五、已知限制与风险

| 风险 | 说明 | 应对 |
|------|------|------|
| Google 翻译非官方接口 | 可能限流或被封，真出事产品当天挂 | 已接受此风险；引擎封装为可替换层；失败时回退原文 |
| YouTube DOM 变动 | 改版导致 `.ytp-caption-segment` 选择器失效 | 监听逻辑集中，及时更新 |
| 字幕叠加层错位 | YouTube 改版可能导致叠加位置偏 | 渲染逻辑集中，易改 |
| 翻译质量 | 免费引擎质量有限，游戏梗/人名可能翻砸 | 术语库（`glossary/ko-zh-game-terms.csv`）校正；后续可换 Claude/DeepL |
| 延迟 | 网络延迟不可控，<1 秒为目标非硬保证 | 缓存+防抖降请求量 |

## 六、下一阶段 Roadmap

按优先级排列（均不在 v1）：

1. **翻译正确性优化**：扩充术语库，覆盖目标主播的常用词/梗/人名
2. **Chrome 商店发布**：面向种子用户（死忠粉社群）推广
3. **账号体系 + Web 控制台**：用户注册、登录、历史记录、生词本（后端已就绪）
4. **显示个性化**：字号调整、位置选择
5. **切换更高质量翻译引擎**：DeepL / Claude（引擎层已封装，可替换）
6. **无字幕直播的语音识别**：捕获标签页音频 → ASR（Whisper）→ 翻译。难度最高，可能需 WebSocket 后端。这是完整愿景的核心大赌注。
